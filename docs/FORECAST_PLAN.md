# Прогноз day-ahead цен CZ: план

Продолжение [первого плана](PLAN.md): прогноз почасовых цен зоны CZ на день D+1, сделанный
до закрытия аукциона (12:00 Europe/Prague в день D), честная оценка на истории и прогноз в
продакшене.

## Принцип «известно на момент прогноза»

Каждый признак для D+1 должен быть известен в 12:00 по Праге в день D:

- календарь (час, день недели, праздники, длина дня, сезон) — да;
- цены дня D и раньше (опубликованы в D−1 около 13:00) — да;
- фактическая погода ČHMÚ за D+1 — нет, только как эксперимент «идеальный прогноз погоды»;
- прогноз погоды, выпущенный до 12:00 D — да (Open-Meteo, см. [sources.md, раздел 5](sources.md)).

Правило закрепляется тестом pytest: признаки D+1 не меняются, если подменить данные,
появившиеся после 12:00 D.

## Итоги этапа 1

- **Источник:** Open-Meteo Previous Runs API, модель **DWD ICON-EU**. Значение
  `previous_dayN` в час T берётся из прогона, инициализированного не позже
  floor_6h(T − N суток); это проверено по Single Runs и закреплено тестом.
- **Без утечки:** используем только прогоны не позже 00Z дня D. Для часов D+1 до 06:00 UTC
  это `previous_day1`, для остальных `previous_day2`.
- **Отброшены:** Historical Forecast API (упреждение 0–5 ч), ECMWF IFS 0.25° (прогон за
  значением не ограничен по времени), GFS (хуже по точности), `best_match` (смесь моделей с
  неизвестным временем выпуска).
- **ENTSO-E:** токен запрошен. Прогноз нагрузки публикуется до 10:00 D, прогноз ветра и солнца
  на D+1 — до 18:00 D (позже cutoff), и оба обновляются; нужна версия, опубликованная до 12:00.

## Итоги этапа 3

- **`ml.ml_features_hourly`**: строка на UTC-час дня поставки D+1 (23/24/25 в день), с
  `forecast_date` = D и `cutoff_at_utc` = 12:00 по Праге в день D. Строки есть и для завтра
  (цель `price_eur_mwh` пока null).
- **Признаки:** календарь (час, позиция в дне, будни, праздники, соседние рабочие дни, сезон);
  цены D и D−6 в тот же час, статистика цен за D−6…D; прогноз погоды по CZ (температура,
  радиация, ветер 10/100 м, облачность), солнце юга Германии и ветер севера Германии, средние
  за день.
- **Прогноз погоды на cutoff:** `int_openmeteo_forecast_at_cutoff` берёт самый свежий прогноз,
  опубликованный до cutoff (`issued_at` + 6 ч ≤ cutoff), то есть прогоны не позже 00Z дня D.
  Радиация для часа H берётся из строки H+1 (Open-Meteo метит среднее за час его концом).
- **Фактическая погода** вынесена в `ml.ml_oracle_weather_hourly` только для эксперимента
  «идеальный прогноз».
- **Проверки:** dbt-тесты на `known_prices_through ≤ forecast_date`, на время выпуска погоды,
  на полный набор часов в дне и на прогноз погоды для каждого часа с ценой. Pytest
  `tests/test_ml_features_leakage.py` собирает признаки настоящими dbt-моделями на синтетических
  данных и сравнивает D+1 при трёх состояниях базы: «вовремя», «поздно», «поздно с другими
  значениями». Признаки совпадают; изменение данных до cutoff их меняет. Тест проверен
  намеренными ошибками (задержка 0 ч, окно цен до D+1): оба раза он падает.

## Итоги этапа 4

- **Модуль** `src/energy_pipeline/forecast/` и CLI `forecast validate | backtest | importance`.
- **Настройки выбраны на валидации** (2025-09-01…2026-02-28): цель — сама цена (гипотеза
  «отклонение от недельного уровня» не подтвердилась), LightGBM с L1, 500 деревьев; Ridge с
  alpha = 1000; интервалы — квантильный LightGBM с конформной калибровкой по последним 28 дням.
- **Тест** (2026-03-01…2026-10-29, 243 дня, ежедневное переобучение): LightGBM с прогнозом
  погоды MAE 21,29 против 32,45 у «как вчера» (−34 %) и 38,76 у «неделю назад»; лучше
  бенчмарка в 193 днях из 243. Погода даёт 4,6 EUR/MWh, идеальная чешская погода — ещё 0,2.
  Интервал p10–p90 покрывает 75,6 % часов при номинале 80 % (без калибровки было 63 %).
- **Важнее всего** недавние цены, затем ветер и солнце Германии, потом чешская радиация.

## Итоги этапа 5

- **`forecasting/report.ipynb`** (на английском): задача и принцип «известно на момент
  прогноза», признаки, схема оценки, выбор настроек на валидации, результаты на тесте,
  ценность погоды, ошибка по времени, сезонам и часам, прогноз против факта (последняя неделя
  с DST-днём и неделя 1 мая с ценой −500), интервалы, важность признаков, выводы и ограничения.
- **Логики в ноутбуке нет:** таблицы и графики считает `energy_pipeline.forecast.report`,
  числа в тексте подставляются из результатов.
- **Одна команда:** `uv run forecast report` (с `--refresh` сначала пересчитывает валидацию,
  бэктест и важность признаков, около 25 минут).
- Графики — Altair в палитре дашборда, сохранены как SVG (GitHub показывает их без JavaScript;
  ноутбук весит около 200 КБ).

## Итоги этапа 6 (код)

- **`forecast.yml`**: 04:13, 06:37 и 08:53 UTC → `pipeline morning` (цены D и свежие прогнозы
  погоды) → dbt-сборка признаков → `forecast predict`. Первый успешный запуск пишет прогноз,
  следующие видят его и выходят.
- **`ml.price_forecast`**: LightGBM (цена, p10/p50/p90) и оба бенчмарка; `issued_at`,
  `is_late`, `model_version`, `code_version`; `run_type` = live или backtest.
- **Отказ вместо плохого прогноза:** если для D+1 нет всех часов, цен D или прогноза погоды,
  команда падает.
- **Оценка:** `ml.ml_forecast_accuracy_hourly` и `ml.ml_forecast_daily_metrics` строятся в
  дневной сборке, когда цены D+1 опубликованы; свежесть `ml.price_forecast` проверяется.
- **История для дашборда:** `forecast backfill-history` (или ввод `history_from` у
  workflow) пишет walk-forward прогнозы с 2026-03-01; они совпадают с результатами этапа 4.
